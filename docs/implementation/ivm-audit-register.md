# Delta-batch (IVM) mode audit register

Source-to-sink review of delta-batch mode across embedded / single-node /
distributed, and across the SQL, Python, Rust, CLI, HTTP and MCP surfaces
(2026-08-23). Six parallel reviewers; every claim below was reported with
file:line evidence, and the ten highest-severity ones were re-verified by
hand against the source before this register was written.

**The standing rule (inherited from the crate-audit register): every test
added must be checked to FAIL against the pre-fix behaviour.** Revert the
one production line the fix touches and watch the new test go red. A test
that cannot distinguish correct from broken is worse than no test.

**Three ways a revert-proof lies, all of which happened during this pass and
each of which was caught only by actually running the revert:**

1. *The fallback mask.* When the fix degrades to a slower-but-correct path
   (DiffBased instead of an O(Δ) plan), a test asserting only the right
   **answer** passes before and after — both paths compute it. CORE-23's first
   test did exactly this and had to gain a plan-kind assertion before it could
   fail. If your fix has a correct fallback, assert the property that
   distinguishes the two paths, not just the output.
2. *The pre-existing signal.* A test asserting a reason string, a status, or a
   counter that the pre-fix code also set is not a proof. PART-20's first test
   asserted a stop reason the old `continue` shape recorded too.
3. *The trivially-passing baseline.* A test for "old format still loads" passes
   before the fix because everything was the old format (PART-8), and a guard
   against over-rejection passes before the fix because nothing was rejected.
   These cannot be revert-proven at all; prove them against the obvious **wrong
   fix** instead, and say in the register which of the two you did.

Where no proof is possible, write that in the row. An unproven test recorded as
proven is the same defect class this register exists to find, one level up.

**Status values:** OPEN | FIXED `<commit>` | PARTIAL | WONTFIX (with reason) |
RESOLVED-AS-DOCUMENTED | DECIDED (product decision recorded, no code change).

## Structural finding (the headline)

There is **one** maintenance engine. SQL DDL (`CREATE INCREMENTAL VIEW` via
`START PIPELINE`), `DataFrame::to_incremental`, `Session::ivm`, the CLI, the
HTTP registry and MCP all converge on `krishiv_ivm::IncrementalFlow`. There
is no duplicate implementation of incremental maintenance — the disease the
streaming convergence (task #150) had to cure is absent here. The defects
below are in the engine itself, in the transport into it, and in the
honesty of the surfaces around it.
